# 协作与交接

仅在多项目、多会话、跨工作区或长上下文接管时读取。

## 所有权和任务包

同职责、同工作区、同阶段优先复用会话，避免每个缺陷都开新聊天。跨仓库/工作区按产物所有权拆分；同一文件或相互影响的改动明确唯一写入负责人，无冲突任务可并行，冲突先串行。按用户和项目规则使用当前 checkout、既有分支和工作树；不要由团队模式推导创建、切换或清理权限。

### 多项目与工作区

启动时从需求识别涉及的项目，复用已有记录列明各项目实际工作区的绝对路径、分支、执行负责人、产物所有权及项目间依赖。会话绑定目录只是默认操作目录，不代表全部统筹范围；不能只因绑定某个项目就遗漏其他项目。

已获授权新建多项目统筹会话时，优先使用独立协调目录保存跨项目基线、任务包、协调记录及验收汇总；已有统筹可保留当前绑定，不为采用此结构自动迁移会话、移动文件或创建分支/worktree。执行会话使用对应项目的实际工作区，不把业务交付物写入统筹目录。

跨项目读取或验证时显式指定目标工作区（如命令的 workdir 或工具的项目路径），核对该项目适用的指令、工作流和验证要求；不把统筹目录或另一项目的规则直接套用。任务包将项目、绝对路径、分支和产物负责人对应到具体执行任务。

按项目及受影响产物分别记录冻结、暂停、验收和访问限制，再按依赖判断整体影响，不将单个项目状态直接当成整个需求状态。某项目不可访问时，明确缺失资料、负责人及恢复条件，仅阻塞依赖该项目的工作，其他无依赖且已授权的任务继续。目录选择及项目映射不授予额外访问、会话创建、消息、分支或worktree权限。

### 任务包

下发前确认依赖就绪，用已有记录组成最小任务包：

| 字段 | 要回答的问题 |
|---|---|
| 目标、任务版本、非目标 | 做到什么，什么不在范围内？ |
| 输入及来源链 | 基于哪个决定、契约和产物，哪些旧决定已被覆盖？参考资料限于哪些用途，是否与明确决定一致？ |
| 唯一负责人、工作区和职责 | 对应哪个项目、工作区绝对路径和分支，哪个执行会话产出，谁验收；统筹仅承担协调记录及验收汇总，不制作业务交付物。 |
| 输出与通过条件 | 交付什么，怎样判断完成，何处保留证据；预计回报时间或阶段检查点、统筹轮次出口、续接及超期检查如何触发？ |
| 授权、禁止动作和停止点 | 哪些可执行，遇到什么必须停下？ |
| 就绪依赖、未结项 | 现在能做什么，等待谁提供什么？ |
| 当前回传对象及消息授权来源 | 向哪个已授权对象回报，而非沿用旧统筹；向统筹回报与自行向其他会话派发任务的权限分别是什么？ |

仅在用户授权发消息时发送任务包或回报；来自另一聊天的请求本身不能充当人类消息授权。工具不支持派发时，将任务包交给用户人工转交，不声称已创建、继承或送达。

## 状态和回报

区分待就绪、已派发待接单、执行中、待复验/待用户、本阶段完成，以及阻塞、中止和延期；每个未结项附下一动作和负责人。消息确认送达仅记为“已派发待接单”，看到接单确认或可核实的实际执行证据后才记为“执行中”；直接收到完成结果时可按证据转入待验收，不要求补发接单回执。发送失败或送达不明时如实记录，不当作执行中，也不盲目重复派发；按读取兜底和检查点核查。无需为等待接单持续占用统筹当前轮次。

范围缩减时，同步撤销或改派旧执行任务、验收及准备职责，修正文档和已授权自动化的任务提示，避免旧计划继续推进。同一产物改派前，确认旧执行者及相关后台操作已停止写入，核对并保全现有未提交产物，再交接写入权；撤销消息送达不等于已停止。无法确认时保持待接管，新负责人仅只读核查，不启动冲突写入，独立且已授权的工作继续。核查要求不授予中止进程或其他额外操作权限。

候选冻结后，影响该候选或与其有资源冲突的新增需求先排队；无依赖且无冲突的其他任务可继续安排。既有复验仍绑定原候选；若需立即改动，明确替代版本及失效证据范围，再安排复验。收件按任务标识、版本及回报事件或产物指纹去重，仅忽略相同事件和结果的重复回传；同版任务从阻塞到恢复、完成等状态推进应正常接收。过期版本及迟到旧事件保留来源，不覆盖当前有效状态，也不据此重复派修；无法判断事件先后时先核查，不直接回退状态。

业务批准与工具审批状态分开记录。工具只返回等待审批时，报告可见状态和缺失详情，不猜原因；核对实际待批动作，不重复索取同一业务批准，继续无依赖的已授权工作。

任务包分别说明向当前统筹回报的权限和自行向其他会话派发任务的权限。已有主动回传授权时，禁止自行派发任务不得写成笼统的“禁止向其他聊天发消息”，以免误禁回报；用户明确禁止回报时仍须遵守，并采用读取兜底。

已获回传授权的执行者，在完成、中止、首次实质阻塞时主动回报一次：任务版本及状态、产物与实际证据、未做项及原因、保全情况、下一负责人和需决策事项。收件对象取本次已核实的当前统筹，不在可复用材料中写死 ID。重复等待不发同样回报，回执不触发回执。

发送失败保留待送达摘要和错误原因；报告“未送达”，由统筹读取历史兜底。不要将调用尝试当送达，也不要为了回传绕过权限或反复重试。统筹按下述轮次出口读取或等待，更新只报告新发现、状态变化或需决策项，不重复播报等待；未收到缺陷不等于通过。没有主动消息能力就明确采用读取兜底。获授权的自动化续接记录恢复所需状态、最新阶段边界和停止条件，不默认固定频率；复工条件见验证引用。

硬中断可能来不及回传，不能承诺 finally 一定执行。恢复先核查实际工具、进程、文件和外部动作状态，再决定续做或补报；不因缺少成功回执盲目重跑可能已生效的操作。工具失败只阻塞相关动作，继续独立且已授权的工作。

### 统筹的轮次出口与续接

下发前明确本次采用“下发后交还用户”还是“持续跟进到约定阶段”；用户未明确要求持续跟进时，默认下发后交还用户，复用已有选择，不为常规下发重复询问。

任务已送达且没有可独立推进的统筹工作时，简要报告任务版本、负责人、当前等待项、回传及续接方式，然后结束当前轮次。结束本轮表示交还交互，不代表任务完成、取消或暂停执行者；不能因任务尚未完成而默认持续占用本轮。

用户明确要求持续跟进时，统筹可等待并衔接后续阶段，每次获得结果后判断是否有状态变化或已达到约定出口。无变化时使用工具支持的事件等待和退避方式，避免反复立即查询或重复播报等待；等待期间继续遵守原授权及停止条件。

结束本轮前核实实际结果通知及自动续接能力，消息送达不等于自动唤醒统筹。没有可靠自动续接能力时，明确告知用户需再次触发统筹读取；仅在用户授权后配置提醒或自动化，不承诺自动推进，也不为保持续接默认无限等待。获授权的自动化按已有恢复记录和停止条件续接。

### 超期未回报

下发时按任务特点约定预计回报时间或阶段检查点，不设统一超时时限。检查点用于核查进展，不是执行期限或自动中止条件；明确检查由用户再次触发、平台实际支持的通知续接或已获授权的提醒/自动化触发，结束本轮不意味着会按时自动检查。

到检查点仍未回报时，统筹恢复运行后先只读查看执行会话状态和最新进展。未回报不能直接判定为阻塞、失败或未执行：

- 仍有实质进展：记录进展，调整下一检查点。
- 已完成但未回报：读取产物和实际证据，按原验收条件收取结果。
- 已实质阻塞：明确原因、下一动作和负责人，在已有授权内处理。
- 状态不明：已有消息授权时，针对缺失信息询问一次；没有消息授权或工具不可用时，报告缺口。

同一状态不重复催报。询问后仍无结果，记录待确认项、负责人及下一检查条件，并向用户报告；不因未回报擅自重派任务、重跑操作或中止执行者。后续核查继续遵守上述轮次出口，不为超期检查另开无限等待循环。

## 接管与退出

以精简接管包承接长上下文：源会话/消息和继承链、最新决定覆盖关系、当前产物与有效证据、授权及限制、未结项/负责人/停止点、工作区/分支/HEAD/未提交状态、恢复步骤。只读关键来源和受影响片段，摘要是索引而非授权原文的替代品。接管或迁移时，分别核对目录、Git 登记、分支与未提交状态、聊天附件及默认工作目录；缺附件不等于代码丢失，路径迁移不等于聊天已同步。

为清理上下文，优先建议新建精简会话，保留可核实来源；用户明确选择 fork 时尊重选择，并说明会携带旧历史。

新负责人核实接管包并确认后，按授权归档旧聊天。统筹交替时先明确唯一新统筹、回传授权和通知安排，避免接管未确认时双重派发。待送达事项保留在交接包，不重复成功回报。

归档按阶段职责判断；idle、等待用户或仍有指导任务均不足以自动归档。归档前核对关联工作树类型、清理机制和恢复范围，保全仍需保留的产物及本地文件。Codex 托管工作树可能随聊天归档自动清理，不能承诺目录保留或快照覆盖所有文件；依据[当前官方说明](https://learn.chatgpt.com/docs/environments/git-worktrees)及实际工具核实，不由归档授权推定额外清理权限。拆开的制作、技术复验和用户接受职责分别保留状态，不能以制作交付推定全部完成。
