# 现状业务梳理文档

仅在用户要求生成、更新或审查重构前的业务流程与实现现状时读取。沿主 SKILL.md 的文档口径与取证规则调查；本文记录可核查的现状，不制定目标需求。

## 文档拆分与职责

先按[迁移范围](../SKILL.md#选择迁移范围)确定本次现状对象：仅前端写页面事实及必要接口摘要；页面相关的仅后端可只写指定接口/项目处理与保留页面的消费摘要，不强制为每个消费者新建整篇页面现状。未修改项目只取证本次兼容所需部分，不把目录拆分当作改造范围。

多页面现状文档按[层级与拆分规则](markdown-delivery.md#适用范围与目录)组织：各页面独立，现状总览说明旧链路、页面与后端关系、共享逻辑归属及取证缺口。后端现状在复杂或共享时按需独立，可按项目拆分；不因存在依赖就为每个项目建文档。单页本地任务直接交付所需片段。

页面现状写接口触发、顺序、参数来源、响应消费及对展示和后续操作的影响，可附代码位置、关键表达式或短片段，不逐行解释源码。后端现状集中写鉴权、业务分支、下游调用、数据读写与副作用；完整字段和错误契约归旧接口文档。共享逻辑主维护一处，各页面保留自身差异及必要摘要，不以引用省略页面行为。两类现状都记录事实和证据，不写拟定的新实现。完整内容归属沿[归属规则](document-review.md#文档归属与同步)。

## 取证与写法

- 标明调查范围、现有前后端代码所属项目及仓库链接、代码版本、旧前端页面的实际访问地址和依赖的文档版本。用户提供旧需求文档时附其链接；无法核实的地址或版本标明状态，不编造。
- 对每项结论给出可定位的证据；区分已观察的行为、已确认的业务规则、已确认的 Bug、推测和未知。
- 沿用户场景梳理身份、入口、页面状态、操作、分支条件及优先级、权限、时间与金额边界、数据范围和业务副作用。记录失败时用户看到的文案、可执行动作与状态恢复。
- 逐状态记录实际渲染的区域、字段、按钮、链接与文案；逐操作记录入口、可用条件、二次确认、提交中反馈、成功及失败后的状态。表单写字段必填、格式、范围、关联校验、触发时机与逐项提示；列表写筛选、排序、默认页、页码与每页条数、条件变化时的页码处理和空结果。页面跳转写可见文案和实际目标地址。接口错误除内部码外，还要写用户看到的文案与呈现方式（toast、dialog、页面内提示等），并核对公共拦截器和页面是否重复处理。
- 尽可能获取对应旧页面的截图，覆盖首次进入、不同角色或关键业务状态、空数据、表单校验、确认弹窗和典型错误提示；只选能证明差异的画面，不为凑数量重复截图。为每张图标注页面地址、环境、角色、状态、截取时间和对应文档章节，并核对截图与当前代码版本是否一致。页面无法访问、数据缺失或截图不能取得时说明原因及改用的证据；截图只能证明画面现状，不能单独证明业务规则。
- 现状梳理概述页面直接调用的接口及其触发阶段。旧接口文档按接口记录请求与响应、空值、特殊错误码及序列化类型、公共拦截器和页面动作；仅链接实际存在的本地章节或配套 Markdown 文件；必要时记录代码位置、配置、数据来源、下游调用和其他调用方。只追到足以解释业务结果与迁移风险的层次。
- 现状梳理与旧接口均如实记录旧实现，不把修复后的目标倒写为旧事实。已确认 Bug 在实际发生的页面状态、业务规则、操作流程或接口结果的**原描述位置**紧邻标注“此处存在 Bug：编号”，将编号链接到独立“Bug 汇总与修复方案”文档的对应条目；同一问题涉及多处时逐处引用同一编号。本文不设置 Bug 汇总章节，不另展开诊断或修复方案；详情及稳定编号规则见[Bug 文档指导](bug-register.md)。无法证明的问题单列待核实，不标为已确认 Bug。
- 来源冲突、无法复现或缺少证据的事实列待核实；只有缺失决定会改变本次目标或验收时才列待确认，并说明具体影响。未检索的仓库外消费者不自动成为待决策或阻断项，调用关系按下文记录。

## 推荐结构

1. 范围与来源：页面、角色、现有代码项目及仓库链接、代码版本、旧需求文档链接、旧前端页面地址与覆盖边界。
2. 页面画面与截图：按角色和状态列出实际渲染内容、文案、链接和截图；不用无业务意义的样式尺寸。
3. 业务流程与交互：按用户场景描述入口、判断、展示、操作、二次确认、结果及副作用；表单校验、筛选排序、分页和跳转单列规则。已确认 Bug 发生在哪项描述，就在该项旁标记并链接编号。
4. 页面与接口对应：初始化与交互分别概述请求、成功和失败状态，以及错误提示文案和呈现方式；详细契约与错误码放旧接口文档；仅在对应章节、文件或页面已存在时从此处链接。接口结果涉及已确认 Bug 时，现状梳理与旧接口各自在实际相关描述旁标记并链接同一编号。
5. 业务规则与边界：身份权限、状态、时间金额、排序、空数据及前置条件；标明来源和确认状态，已确认 Bug 发生在哪条规则，就在该条旁标记并链接编号。
6. 依赖、其他调用方和待确认事项：只写与本次范围相关的影响；待核实问题与已确认问题分开。

已确认问题的原位标记指向独立 Bug 文档，不再在本篇重复登记。需要的汇总文档未获交付授权时列明待补项，不创建空白文档或伪造条目链接。

## 旧接口文档与发布

按页面实际调用识别接口并按提供项目归属；同一契约集中维护，标明消费页面及触发、参数、错误消费差异，不按页面重复抄写。逐接口记录旧接口的路径和方法、触发时机、身份、请求字段、成功响应、空值、特殊失败码及序列化类型、对应的实际提示文案与 toast/dialog/页面内等方式、前端处理、状态恢复、证据和其他调用方；初始化与用户交互分开。本地交付时，按用户所需载体将旧接口文档作为现状梳理的章节或配套文件。若尚未取得接口证据，明确待补范围，不创建空白占位页。

涉及其他消费方时，以本篇对应接口为主记录：消费页面/模块、用途、使用字段或错误动作、代码位置与版本，以及已检索的仓库边界；“本仓未发现”不等于全局不存在。现状梳理保留摘要和定位链接，方案仅承接实际兼容影响，不另建重复清单。调用关系本身不生成修复任务；修复与验收范围按[Bug 文档指导](bug-register.md#登记与确认)判断。

旧接口只记录对应旧版本的实际契约；已确认 Bug 在其发生的鉴权、分支或结果描述旁标记并链接独立汇总条目，不附诊断、修复方案或目标契约对照。

更新已有 Markdown 文档时，按[Markdown 交付](markdown-delivery.md)保全最新正文并核对引用。

文档可以含内部错误码、接口字段、代码位置和证据链接。若另写重构前或重构后产品需求文档，只将已确认的业务含义和用户可见结果转入产品文档；问题编号、旧问题与修复过程不进入产品文档。

生成、更新或正式审查文档时，按[文档审查与验收](document-review.md)核对本轮范围及交叉口径。
