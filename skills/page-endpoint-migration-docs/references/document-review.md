# 迁移文档审查与验收

生成、更新或正式审查迁移文档时读取；只核对用户要求的范围及实际存在的交付物，以本地 Markdown 记录审查结果。文档归属与同步按本篇[对应小节](#文档归属与同步)执行。更新已有文档时按最新版本保留无关编辑并核对引用；目录和文件更新按[Markdown 交付](markdown-delivery.md)处理。

## 表述歧义检查

生成或更新各类文档时，按[共用表述规则](../SKILL.md#文档表述与歧义处理)检查本轮正文；审查时只报告授权范围内的问题。以读者能否确定适用条件和结果为准，不能只查有无某个词。

| 检查点 | 判定方式 |
|---|---|
| 主体、对象与范围 | 能确定谁执行、作用于哪些记录或页面状态；同一概念的称谓一致，简称及跨篇引用能定位具体条目。“当前”“全部”“相关”等须有明确范围。 |
| 条件与边界 | 能区分条件的与/或关系、处理顺序及冲突优先级；涉及数值、时间或空值时，边界、单位及判断口径完整。来源只写“为空”时，不能自行认定字段缺失、null、空串和空白文本等价。 |
| 动作与结果 | “成功”“刷新”“同步”“恢复”等动作或状态有具体含义；例如区分请求成功与业务成功、重查列表与整页重载。按文档职责写清可观察结果或契约，不向产品正文混入技术字段。 |
| 不确定项与原文 | 已知事实、未决规则和未执行验证分别记录；待确认项能指出缺少哪个决定及影响。准确文案、标识和引文未因含模糊词而被改写，也未被当作实际行为或耗时证据。 |

发现两种会导致不同实现或验收结论的合理解释时，写出具体分歧并回查依据；能确定的直接改清，不能确定的按下文分类记录。未决范围不能写成已可实施或已通过，已明确的范围仍保留其结论。不为消除文字歧义新增业务规则，也不把原文中的模糊措辞直接判为设计缺陷；涉及并发承诺时，按[校验与保证的区别](migration-plan.md#前后端实施与联调)核对已确认目标与方案能力。

## 文档更新与交叉核对

### 文档归属与同步

在用户已授权的文档中，按内容影响选择更新范围；技术方案变化不要求机械同步全部文档。补证、纠错和新决定先归入对应主题、规则或用例，替换失效说明；确需新增专题时按主题命名。更新后的正文应是可直接使用的当前说明，编写与复核过程放交付说明，版本化正文的历史处理见[Markdown 交付](markdown-delivery.md#当前正文与历史)。

用户新决定明确替代旧要求时，反查受影响的正文、摘要、接口、用例及门禁结论，清理失效要求、待定与阻断项，保留决定来源；未获更新授权的文档列为待同步，不继续按旧要求验收。连续确认时逐项在本地 Markdown 保留来源与生效决定，按实际影响合并更新已授权的正文。影响在途工作或依赖的决定及时写入本地待同步事项，标明受影响方、关联文档及影响。该清单随本地文档交付，由用户安排通知或后续同步。用户要求逐项确认时仍按其要求执行。

| 文档 | 内容归属与更新条件 |
|---|---|
| 迁移总览 | 业务目标、范围与排除项、关键链路、页面/端/项目关系、阅读入口和整体状态；不复制完整规则、契约或实施步骤。 |
| 现状总览 | 旧链路全貌、页面与后端关系、共享逻辑归属、取证覆盖与缺口；不重复各页全文。 |
| 页面现状梳理 | 旧页面展示、操作、状态、准确文案；请求触发与顺序、参数来源、响应消费、必要代码位置和短片段。完整契约归旧接口，诊断与修复归 Bug 文档；已确认 Bug 仅原位标记编号链接。 |
| 后端现状梳理 | 旧鉴权、处理分支、下游调用、数据读写、副作用、共享逻辑和代码证据；复杂或共享时按需独立，不写拟定的新实现或重复完整契约。 |
| 重构前产品需求 | 已核实的现行用户可见条件、操作、展示、准确文案和结果，区分已确认沿用与仅观察到的规则；不写代码、接口字段、内部错误码或 Bug 内容/编号。 |
| 重构后产品需求 | 已确认的目标业务规则、页面与端差异、准确文案、操作结果与验收场景；不写技术实现、Bug 内容/编号或未确认的实现行为。 |
| 旧接口文档 | 实际请求/响应、类型/空值、鉴权、错误语义、必要消费约定、其他调用方及证据；不倒写目标契约或重复完整页面和后端流程。Bug 仅对应描述旁原位链接编号。 |
| 新接口文档 | 目标请求/响应、校验、鉴权、错误语义、兼容与必要消费约定、提供项目规范依据；不写页面状态管理、请求调度实现或 Bug 内容/编号。 |
| 开发方案总览 | 修改与依赖项目、职责、共享技术安排、任务依赖、跨项目联调、发布顺序/回退、开发发布表；不复制全部页面方案、产品规则和字段表。 |
| 页面前端方案 | 路由入口、组件复用、页面状态、请求编排、校验落点、错误处理、跨页交接、必要行为摘要及验证；不重复完整后端实现、契约或 Bug 专项修复设计。 |
| 后端开发方案 | 各项目改动落点、分层与定义、业务处理、下游适配、错误映射、副作用控制、兼容及验证；不重复完整页面交互和契约，不新增未确认业务规则。 |
| 入口切换等专项方案 | 已确认事项的对象、规则、落点、依赖、发布回退和验证；不扩展为未授权旧系统改造或下线。 |
| 测试用例 | 来源、条件、数据、步骤、准确预期、控制/观察边界和业务场景覆盖；不从实现反推预期，不写 Bug 内容/编号或诊断。 |
| 测试执行记录 | 文档及代码版本、环境、结果、证据、失败和未执行原因；可与用例同篇，执行结果不替代目标规则，待执行不记通过。 |
| Bug 汇总与修复方案 | 独立维护现象、判定与诊断、确认状态、修复对象、专项修复设计、兼容影响、关闭条件及证据；链接目标/接口/任务/用例，不替代它们自身内容。 |

共享内容有一个明确主维护位置：同一接口契约不按页面重复，后端共享逻辑集中说明；各页面保留自身触发条件、参数/消费差异、可见结果及定位链接。修复任务旁只注明“修复 Bug：编号”并链接详情，常规技术安排仍在方案。

跨页面业务步骤与交接结果归产品，旧交接事实归现状，传值与恢复机制归方案，贯穿验证归测试。业务结果与技术机制分别描述，例如登录后的去向归产品，登录错误语义归接口，拦截与回跳实现归方案，操作与预期归用例。事实、目标、方案、实现和验证状态分别维护，不能互相充当证明。

调整内容归属时，先检查目标文档是否已有对应说明，已有则合并，缺少才迁入；取证推导与实现细节在所属技术文档集中维护，其他篇保留符合自身职责的摘要与定位链接。需求和接口各自的文档集合仍须写全其适用规则、字段、条件、准确文案、边界与结果；各篇明确自身范围，共用规则可定位到同类文档主描述，不能引用其他类型文档代替自身必需内容。同篇规则有明确主描述，其他位置按需摘要或引用。整理时保留独有信息、原有编号和锚点，按实际条目核对来源语义，不因归并而改变业务范围或用例预期。

### 本轮更新核对

- 交付前按所选参考文件检查证据、未决项、文档间口径及渲染结果。范围变化时，按最新决定反查各篇实施任务及用例的前置条件、数据、操作、预期和验证方法，核对实际对象与停止点；总体范围声明不能抵消条目中的越界要求，不能只确认编号或关键词。范围或编号变化涉及引用时，清理失效引用并更新来源版本。
- 仅修改用户已授权的文档，其他不一致列明。
- 在现有主文档或交付说明集中维护当前交付状态，其他正文按职责保留必需内容并引用当前入口。历史快照保留原时点，明确标识已替代状态。已有收取证据时，按其中实际核对的正文、版本和范围记录收取状态。仍待收取或通知的事项仅写入本地 Markdown，分别记录稿件完成和待同步状态。
- 同时核对当前摘要、门禁结论、用例数量/执行状态和实际维护的版本信息；新证据或决定归位后，清理被替代的待定与阻断结论及不存在的章节引用。只有出现反证或相关变更时才重新提出已确定事项，保留其他条目的有效结论。主文档与历史的处理按[Markdown 交付](markdown-delivery.md#当前正文与历史)，冻结取证基线不冒充当前引用版本。
- 对有语义的符号、项内空白、边界示例和准确文案，从本轮渲染正文核对原字符是否保留；存储源码正确或表格存在不能证明Markdown/平台转换后的内容正确。

整理交付前，按实际改动检查信息组织：新证据与决定已归入主题正文，同篇规则有明确主描述；其他篇的引用仍保留独立使用必需的业务或契约内容；清理历史未丢失独有条件、原文和边界示例。对移位的规则、接口、用例及Bug逐项核对稳定编号、锚点和引用语义；链接能打开不能证明引用的条目正确。涉及主文档时，核对阅读导航、当前状态及开发发布表的项目范围和未知字段处理。作者复核过程写在交付说明，正文记录仍有效的结论与依据。

交付方案或测试用例前，按关键业务场景核对实际存在的重构前后需求、开发方案、新接口文档和用例：数值结果与精度、完整文案、错误条件及页面动作须一致。发现冲突时标出涉及文档；已有明确目标决定的按决定处理并标记待同步文档，尚无决定的列为待确认，不自行选一个版本，也不为检查而补建未要求的文档。


## Bug 归属与修复覆盖（涉及时）

涉及 Bug 登记、标记或修复引用时，按[Bug 文档指导](bug-register.md)核对实际存在的相关交付物；不因审查自动创建配套文档。

- 现状梳理及旧接口仍写实际旧行为，Bug 在原描述位置标记；编号指向独立汇总文档的具体条目，汇总条目能回到来源位置。不得只链接首页，也不在现状梳理内另设 Bug 汇总。
- 按[编号与文档引用](bug-register.md#编号与文档引用)核对详情归属、原位及任务引用；目标规则不能靠 Bug 文档补全。
- 已纳入修复的问题按[修复对象与共享影响](bug-register.md#登记与确认)核对目标规则、接口及可区分原触发条件的用例；不把缺陷来源或调用关系列为当然的修复要求，也不漏掉已纳入的旧入口或实际共享影响。由汇总文档链接目标和用例；缺失则报告具体设计缺口，未授权的文档列待同步。
- 确认、修复范围、实施和验证状态分开；未核实问题不冒充已确认 Bug，方案或待执行用例不能作为修复完成、问题关闭的证据。

## 文档设计验收与实施验证

审查先声明本轮评估的是设计、已落地实现还是测试执行；文档定稿按已确认范围及实际存在的交付物判断。交付说明分别报告设计门禁结论、剩余文档缺陷或待确认业务规则、代码实施及用例执行状态，复用已有栏目；无缺陷或待确认项时明确写“无”。待环境验证写清对象、阶段、方法及停止点，不能笼统列为文档阻断，也不能记为执行通过。

在现有审查说明中记录本轮适用技能的提交号；含未提交改动或无法取得提交号时，记录已读取技能文件的正文指纹。旧通过结论只适用于当时规则及文档快照；技能要求变化时，按新增或变化要求重新核对受影响项，不自动沿用原门禁数量或结论。

| 分类 | 判断与交付影响 |
|---|---|
| 文档设计缺陷 | 已确认结果缺失、相互矛盾，或关键契约/资源/实现步骤缺失导致结果无法确定、方案不可执行；阻断受影响的设计门禁，指出具体缺口。 |
| 待用户决策 | 证据或目标存在会改变业务结果的歧义，且没有有效决定；列出选择与影响，依赖该决定的门禁不能判通过。 |
| 待实施验证 | 规则及契约已可确定、方案和验证控制手段明确，但代码、运行时、账号、联调或部署尚未验证；如实列为未实施/未执行，不因这些事项尚未完成而阻断设计定稿，执行状态仍不得记为通过。 |
| 已接受的限制 | 用户已明确接受其范围及影响；记录决定，不重复作为阻断。存在明确反证或影响超出该决定时重新评估。 |

缺失关键契约或不可执行步骤不能改名为“待验证”绕过门禁。建议优化与已确认要求分开，不自行升级为交付条件。

每个审查问题写清位置、依据、具体输入或操作下的差异、影响范围及上述分类；阻断问题关联真正缺少目标、契约、用例或实施步骤的门禁。旧消费方的调用记录本身不使新链路的产品↔测试覆盖失败；同一问题影响多个门禁时，分别指出实际缺口，不复制同一范围备注作为多个失败依据。已关闭问题重新提出时给出反证或受影响的改动，不为凑问题数量扩大范围。每轮以最新正文为准，可复用未变化的源码证据；修复复核检查改动及关联项，用户要求完整复审时仍按声明范围完整重扫，不能仅核对作者的修复清单。

## 交付阻断：四类文档集合交叉验收（硬门禁）

同次迁移新增或修改下列任一文档时，先按[迁移范围](../SKILL.md#选择迁移范围)识别实际文档集合及适用检查，不将“四类”理解为固定四篇文件或必须补齐的交付物：

1. 重构后产品需求；
2. 新接口文档；
3. 开发方案（含总览、页面前端、后端及专项）；
4. 测试用例。

沿关键业务场景核对目标、接口、实施落点和用例，包含已确认的跨页面、跨端、跨项目交接。完整审查覆盖声明范围内的全部集合；局部更新先识别共享内容及受影响消费者，核对关联条目与集合覆盖变化，复用未变化的有效证据和结论，不机械重验无关项目，也不能只看修改篇。缺少其他正文或有效结论时记未核对及待同步范围，不假定一致。某类未创建时记录“未创建”，该类文档级比对记不适用，不为验收补建；实际已存在但未读取的相关内容仍记未核对。行为和契约检查按影响判断，不能因缺独立文档或不修改该端就记不适用；可依据用户有效决定、已确认业务规则及既有契约核对。关键依据确实缺失时指出具体受阻分支，不因少一篇文档本身阻断。

### 必须勾选并写入交付说明（通过 / 不通过 / 未核对 / 不适用 + 范围及证据）

| 检查项 | 通过标准 |
|---|---|
| 集合与归属 | 列明实际文档、覆盖范围及有效版本；共享主题有主描述，各篇完成自身职责，必要引用能定位 |
| 链路与项目 | 关键业务场景贯穿页面、端、接口和项目；共享消费差异、各提供项目规范、实施与仅依赖项目及联调/发布回退安排无遗漏或冲突；不适用项注明范围 |
| 表述可判定 | 已按[表述歧义检查](#表述歧义检查)核对本轮各篇说明；确定的规则不依赖读者猜测指代、条件或结果，未决项有具体问题和影响，准确原文保持不变 |
| 产品绿场门禁 | 本轮交付或审查目标产品时适用，按其声明范围满足 [business-requirements.md](business-requirements.md)「绿场可实现」各行；涉及输入处理时，仅凭产品正文可确定各操作的保存、显示、回填与拒绝结果；失败/重试/空态须有**准确原文与按钮文案**，禁止只写「可重试」「通用错误态」 |
| 产品↔接口一致 | 核对本轮受影响的已确认业务规则/产品与既有或目标接口；仅前端也须核对既有消费契约，仅后端也须核对保留消费者。输入处理与校验顺序、阻断时机、必填/可空、关键文案、登录回跳、限流挂载点无矛盾；有矛盾先改文再交付 |
| 产品↔测试覆盖 | 本轮交付用例、审查覆盖或变更影响既有用例预期时适用；产品「验收场景」与已确认目标态在实际相关用例中有对应项，不能因本轮不修改测试文档跳过影响核对。处理差异和校验顺序有区分性输入及准确结果，不能仅写「兼容一致」（另议/不测须显式写出）；存在异步写弹框时，核对等待中再次操作/取消/关闭、失败恢复及已确认的迟到响应场景，按具体操作与预期判覆盖，不以规则编号互相引用代替。无此交互则该子项不适用；重大规则未定或对应场景缺失不能判通过 |
| Bug 修复覆盖（涉及时） | 已纳入修复的问题通过汇总条目关联实际目标规则、接口及用例；原触发条件下按修复后目标判定，不保留旧 Bug 预期，详情与编号不泄入目标文档；原位与任务编号能定位具体条目 |
| 用例可执行边界 | 关键用例的条件可在声明的测试层级制造、结果可观察；聚合接口内部阶段不交给页面 Mock 控制，跨层联调写明控制手段，缺条件的分支显式标受阻 |
| 方案可执行 | 涉及查询处理或新增能力判断时，按[查询处理与能力依据](migration-plan.md#制定与开发者审查)核对方案及其边界结果；按实际修改端/项目写清实施、对接及验证；涉及页面改动时含关键行为摘要，仅后端时含必要消费与可见结果兼容摘要，不要求未修改端方案或无关全页清单，不得整段「见产品」且无内容 |
| 另议不作已确认 | 「另议 / 暂不开 / 待问运维」未写成已确认保持或必验主流程 |
| 自检≠独立审查 | 作者交叉重扫结果写入交付说明；未做用户要求的独立审查时标明「未做独立审查」，不得写成已通过独立审查 |

覆盖核对与语义抽检分别完成：

1. **事实到目标的覆盖**：从本次范围的字段、操作和实际转换/分支列出已确认承接的可见结果，反查目标产品及实际存在的接口、方案、用例。四类文档互相一致仍可能共同遗漏；少量样例通过不能代替覆盖核对。
2. **产品自身可实现**：先只读适用产品文档集合正文，用区分性样例重建各操作的保存、显示、回填或拒绝结果，再对照其他文档。不能唯一确定已确认规则的结果、需从旧代码或方案补答案时，绿场门禁不通过；真正未决的部分保留具体决策点。

复用现有规则表、验收场景或交付说明记录“行为/分支 → 来源与确认状态 → 产品/接口/方案/用例条目 → 区分性输入及准确结果”。只列实际存在、影响本次范围的内容，不强制另建文档。当前审查结论集中维护主描述，其他篇按需摘要引用，不反复复制过程说明。每项门禁的一句证据落到本轮实际核对的条目及范围；仅写“已全文检查”或编号相互引用不能作为通过依据。

需要独立审查时，提供用户决定、范围、原始依据与冻结文档版本/正文指纹，让审查者先作范围内独立判断，再核对作者修复清单；完整审查不能退化成只验证已知问题。审查后正文变化时复核受影响规则及关联项；无法判定影响范围时重扫相关全文。仅修复已有发现不等于新增完成一次完整审查。

交叉验收按实际影响判定适用检查，复用仍有效的核对结论。仅修正状态、链接或准确落实已审定的明确修正时，有权收取方按最新正文回读差异及关联条目，核对语义、引用与适用渲染。核对通过且约定的专业和独立复核已完成时，结束该范围的文档审查，无需因收取状态更新再开一轮独审。若改稿产生新业务含义、契约、安全或兼容影响，出现具体反例，或不能界定影响范围，重新安排必要的专业复核并按既有要求独立检查。设计收口与实施、运行及延期状态分别记录。

未完成上表记录，或本轮适用项有「不通过／未核对」：不得宣称整套文档已按技能验收合格。局部修改完成可按真实结果交付，同时列明已检查、未核对及待同步的范围；只能对证据支持的范围给出通过结论，不能把局部通过写成整套通过。
