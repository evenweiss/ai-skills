# 迁移重构开发方案

方案应使开发者知道改什么、为何这样改、先后依赖及怎样验证，但不把每个页面写成同一套实现。开头按[迁移范围](../SKILL.md#选择迁移范围)标明修改项目、仅依赖项目、保留消费者及验收停止点，并列适用的仓库、版本、页面、接口、模块和需求来源。新增或变更页面地址在本次范围内时，记录旧新地址；新地址尚未确定时询问并标待确认，不编造 URL。仅后端或地址不变的任务记录现有消费入口，不要求新前端地址。

列出旧行为到目标行为的迁移安排，区分等价迁移、已纳入本次范围的 Bug 修复、经用户确认的业务变化和待决策项；Bug 项按下文仅作编号引用，不展开缺陷对照。目标行为不明确时询问用户，未得到答复前列为决策点，不伪装成开发任务。现状业务梳理提供可核查的旧实现与错误码，重构前产品需求提供已确认的业务基线，重构后产品需求提供已确认的目标行为；已有这些文档时引用其版本和条目，缺少时按可取得的证据写明来源与不确定性，不为写方案自动另产三份文档。

按“迁移尚未实施”口径生成方案时，不读取本次迁移已有的方案、变更规格或迁移代码来确定目标规则；只核对目标项目既有的通用规范与代码习惯。用户明确要求依据已落地实现整理实施现状或差异时，按主 SKILL.md 的已落地模式读取实际改动，保留原方案的目标口径，并在独立部分区分已实现、未实现、未验证及与目标不符的内容。旧新错误码、接口字段、代码位置与产品规则的映射放在本方案或现状梳理中，不回填产品需求文档。

## 方案总览与分篇

完整方案按[Markdown 文档组织](markdown-delivery.md#适用范围与目录)组织；先按[迁移范围](../SKILL.md#选择迁移范围)裁剪：全栈包含总览、逐页面前端及后端方案，单端或指定项目仅保留所需方案和依赖说明，不为未修改端建空篇。单篇可兼任总览，只交付用户要求的部分。总览维护修改项目与仅依赖项目、共享技术安排、职责、任务依赖、跨项目联调、发布顺序及回退，开发发布表沿[主文档规则](markdown-delivery.md#主文档与开发发布信息)。

每页前端方案明确各端及前端项目的路由、状态、请求编排、校验与错误处理、交接机制和验证。后端可合篇按项目分章，或按项目拆篇，明确各自入口、定义、处理、下游适配、副作用及兼容落点。跨项目链路说明调用顺序、转换、失败传播和实际副作用；共享实现有主维护位置。接口依赖不自动产生提供方改造任务。

旧地址重定向、菜单替换等已确认事项在总览或专项中写清对象、规则、落点、发布依赖、回退与验证；不默认增加入口改造或旧系统下线。页面必要行为摘要放对应前端方案，不在总览复制所有页面规则；完整接口契约集中在接口文档。内容分工沿[归属规则](document-review.md#文档归属与同步)。

## 制定与开发者审查

按所选范围以对应开发者视角阅读旧行为、接口和已确认需求，以及实际修改项目的既有通用代码：前端涉及入口、布局、组件、路由、请求层与错误处理；后端涉及控制器、鉴权、服务分层、下游客户端、响应与配置。未修改端只查解释契约、消费和兼容所需的证据；可靠接口定义、样本及消费证据已充分时，不为单端任务强制取得另一端全部源码。

**查询处理与能力依据**：推荐具体路径前，沿本次目标涉及的筛选、关联、排序、分页等处理，核对每步作用于完整目标集合、某批数据还是单页结果，所需字段的真实来源，以及步骤先后是否改变最终结果。用能区分拟定路径与目标的边界数据推演结果，核对跨批、跨页或过滤前后等实际相关边界；不满足目标的路径退出候选，不能靠后续局部处理补称满足整体目标。真正缺少的能力证据具体标明，不把已能判定的顺序错误留作联调验证。

区分已存在且适用的能力、有条件可行的方向、待核实的前提和需要新增的能力。沿实际调用链核实候选路径尚缺的能力；数据源、字段覆盖、完整集合规模、批查限制、索引或性能，仅检查会影响该路径成立且尚未证明的项目，不机械索取全套。单个入口缺少参数不足以排除其他路线，底层直读也不足以证明上层无缓存；能力未知不得保证复用可行。同库关联、关系唯一键等是具体路线的条件，不自动成为其他已证可行路线的前提。已证实既有路线无法满足目标时，可在授权范围内提出必要新增并说明依据，不因优先复用保留已证伪路线。

字段、独立查询或时间副本的必要性先核实际消费者及既有契约；本页不消费某字段，不自动产生实时化修复任务，也不授权删除共享字段。同步、补偿或读视图选择仅在目标及所需机制确有该问题时展开，不将可避免的机制转成产品决策前置条件；已确认的一致性要求仍须有可执行落点，不能改称环境待验或擅自降低保证。

若新页面仍跳旧项目页面，在现有范围说明中分别写清取证对象、本次改动、验收对象及停止点。用户明确只校验跳转发出结果时，核对目标地址、参数来源与值、原有打开方式即止；不以接收页加载或业务操作作为通过条件，也不计划接收页适配。

已确认目标包含接收状态、整页加载后的恢复或返回路径时，再追踪接收入口的取值、初始化、必要字段来源及可能污染本次传值的旧状态；只检查影响该目标的分支，按实际入口覆盖刷新或新开页，核对路由参数、内存与浏览器存储的作用域，不假设跨项目共享状态。方案只列已确认需要且获授权的接收页改动，验证止于目标结果可判定处，不扩大到整页回归。

验证安排写清阶段、可控制的依赖与可观察结果；需要接收状态时，可用可靠阻断写请求的观察或 Mock 核对提交前字段来源。实际提交或下游写入仅按已确认的受影响分支规划，执行真实写入另按授权边界处理。源码取证不写成运行验证已通过。

默认规划模式下，目标项目中本次迁移已写出的页面、接口、测试或方案不参与目标推导，仍以迁移尚未实施为口径。形成覆盖范围内项目、必要对接及其发布回退的草案，并区分已确认要求、拟定实现、待决策业务问题和需联调核验的技术契约。

草案完成后按实际修改及边界影响选择以下审查项；未修改端检查必要契约与兼容，不要求其实施方案，不以“已写了前后端章节”代替审核：

- **前端审查**：核对真实入口与路由、现有组件可用性、页面各状态和文案、请求封装及登录跳转、接口字段/空值/码类型、重复请求与支付链接安全、测试数据和可执行验收。指出无法依方案直接实现的步骤、冲突或遗漏，并修订。
- **后端审查**：按入口及每个直接接口分别核对鉴权先后、员工身份与权限，不把一个接口的校验推广到整页；核对业务分支和时间/金额边界、下游接口与 DTO、返回信封与错误映射、支付副作用和敏感信息、既有调用方兼容、隔离测试与回退。指出无法依方案直接实现的步骤、冲突或遗漏，并修订。
- **业务计算审查**：对涉及金额、天数或档位的方案和新接口契约，列出旧计算表达式与证据、拟定的等价计算及精度/取整位置；以相同店铺、日期和档位核对旧链路与拟定新链路的报价分项、页面总额、支付请求金额和支付记录金额，覆盖会产生小数的边界。方案阶段可用代码、只读样本或隔离计算验证，不为核对而发起真实支付。无法核实的结果标待确认；差异不得作为等价迁移写入方案。
- **契约与交接复核（全栈时含跨端联调）**：逐项对齐前后端接口契约、错误动作、状态恢复、发布依赖与联调验收。解决审核发现的矛盾；无法由代码和已确认需求决定的事项标明责任人、影响和决策门槛，不伪称审核通过或实施就绪。

完成审核与调优后，按[Markdown 交付](markdown-delivery.md)输出本地文档。规划稿记录方案与未决项；仅在用户明确要求依据已落地实现整理时记录实施状态，并附证据，不把未经验证的方案写成已落地结果。

## 前后端实施与联调

以下前端、后端、对接联调按本次范围适用，只有实际修改端需要完整实施安排；单端或指定项目仍须覆盖必要对接和消费者兼容，不强制同时规划两端改造。常规迁移内容按本节展开；Bug 专项诊断、修复设计、兼容影响及关闭条件集中维护在独立 Bug 文档，对应实施描述仅引用编号链接，不重复展开。标题、层级和其他章节可按项目调整，但适用工作的实施内容和验收方案要各有清晰归属，不交叉混写；跨端依赖可以相互引用。每类内容都写明改动落点、依赖和风险，并给出对应的验收场景、执行方式、可观察的通过标准、所需环境或数据，以及无法验证的项目。验收应覆盖实际受影响行为，不用空泛的“功能正常”代替。

涉及页面改动的方案自身要有可执行的页面行为清单，不能只说“参见需求文档”；仅后端或指定后端项目则写清受影响的消费条件、字段/错误语义及应保持的页面结果，不展开无关布局、控件和交互。适用的页面行为包括：按角色和状态列出目标 UI 内容及准确文案、可见与禁用条件、交互顺序和二次确认弹窗、表单字段与校验条件/时机/提示、筛选排序与分页状态转换、链接文案及目标地址、初始化和交互后的成功/空数据/失败表现。逐类接口错误写触发条件、实际错误码映射、用户可见文案及 toast、dialog、页面内等提示方式、恢复动作和验收场景；没有来源的目标行为标待确认。产品需求可以作为依据并用条目链接，但关键实现与验收口径仍须在方案中明确。只约束有业务意义的 UI 内容，不规定无依据的具体样式。

1. **前端**：先核对落地项目的路由与页面入口、目录和组件组织、构建及环境配置、接口地址或代理配置、请求封装与拦截器、状态管理、样式及测试习惯。依照现有约定规划页面改动、各状态 UI、初始化与后续交互、确认弹窗、表单校验、筛选分页、跳转、错误提示方式和空态；有意偏离既有习惯时说明原因。验收覆盖入口、首次加载与失败重试、成功空态、交互请求、相关视觉状态及受影响的构建或检查，并写清各场景的预期页面动作与文案。
2. **后端**：先核对落地项目的模块划分、环境与配置管理、接口/服务/数据访问分层、DTO 与响应信封、异常及错误码、鉴权、日志、测试与代码风格。对保留在其他项目的下游服务，记录旧调用的触发条件、方法与请求形状、输入归一化、补查/回退分支、响应转换和特殊状态/错误；目标后端继续调用这些服务，不把服务迁移或以其字段名推定类型，取不到提供方源码或可靠样本时列出联调门槛。新接口路径、HTTP 方法和命名优先遵循落地后端项目现有的接口约定；因已确认契约或调用方兼容要求而偏离时，写明依据与影响。依照现有约定规划接口契约、业务等价性、实际涉及的下游调用、副作用和兼容处理，并在涉及已确认修复的任务旁引用 Bug 编号；具体接口、类和配置项以项目证据为准。验收覆盖成功与各类失败、特殊错误码、身份权限、数据边界、调用方兼容及实际受影响的副作用，并标明测试隔离或环境授权条件。
3. **前后端对接联调**：逐接口核对请求字段与类型、响应及可空字段、错误码和前端动作、身份状态、初始化请求顺序、交互后的刷新与状态恢复；联调地址、代理、环境变量和部署参数按两端实际配置确认。验收用端到端场景检查初始化、后续查询与操作的成功和关键失败路径，记录测试账号与数据、环境、执行证据和通过标准；共享环境写入或部署仍须符合项目授权边界。

**校验与并发保证（涉及时）**：产品写每次操作的数量判断、拒绝结果及已确认的同时操作结果；方案区分每次请求独立校验与跨请求原子保证，技术机制归方案。先查重或数量、再写入，不因校验在服务端就能保证并发下唯一或不超限；按已确认目标写清实际保证程度，不由“并发校验”等措辞推导锁、事务或新能力。已有决定仅要求逐请求校验时，改清措辞并保持该范围；已明确要求跨请求保证时，方案须说明能实现该保证的落点及并发验证，不能以串行用例或待验证掩盖设计缺口。

**请求入口异常（涉及时）**：契约涉及解析、绑定、拦截或鉴权失败时，按落地框架核实发生阶段及能捕获它的处理位置；业务方法内的捕获不能承接进入该方法前的异常。方案写明请求入口至响应的承接路径、HTTP/信封/文案及鉴权顺序，优先复用项目能力，必要的局部适配写清范围，不默认改全局配置。验证从能触发该失败的入口进入，使用项目实际的解析、绑定或拦截配置；仅直接调用业务方法或页面 Mock 不能证明前置错误契约。按已确认顺序核对响应及不应发生的后续调用，不预设所有项目都先鉴权或先解析。

在相应部分按依赖拆出可检查的阶段和完成条件，并交代兼容验证、上线顺序、入口开放条件与回退路径。上线顺序由实际调用关系和部署边界决定；不默认后端、前端或入口的固定顺序，也不把方案视为部署授权。涉及页面状态改动或相应兼容问题时读取 [接口与页面状态约束](page-state.md)，按目标项目的现有组件与已确认设计规划页面状态；不从历史案例照搬接口地址、组件、配置或代码习惯。

缺少环境或仓库时完成可取证部分，并标明无法确认的设计与验证项。

## 问题修复与未纳入事项

按独立“Bug 汇总与修复方案”文档中的确认与范围决定安排任务。已纳入本次修复的问题，在对应前端、后端或联调描述旁仅注明“修复 Bug：编号”，编号直接链接对应条目；同一问题各处引用同一编号，不只在末尾列清单。Bug 详情、诊断、修复方案、兼容影响及关闭条件均在汇总条目维护，方案不另设详细修复表；常规迁移实现与依赖仍按前文写清。

待核实、未获修复确认、范围外或被明确要求暂不修复的问题不自行纳入实施；已有汇总条目保留实际依据与范围决定，方案在相关范围处按需引用。修复对象与共享影响按[Bug 文档指导](bug-register.md#登记与确认)确定，不因旧链路保留就增加修复、风险接受或关闭要求。已有修复任务被调整时同步相关编号引用，不暗中删除已纳入问题。

未纳入的优化、否决建议或明确不改事项，仅记录影响本次范围判断或用户要求保留的决定；归入现有范围主题，必要时集中成表，写清内容、来源与决定、交付影响及已确定的后续安排，不强制独立章节或空表。同一决定保留主描述，其他处引用；不能借整理删除有效依据，也不用“未优化”掩盖已纳入但未修复的问题。

## 新接口文档

新接口文档可作为方案章节或配套文件。跨页面时按接口类组织统一入口，仅链接实际存在的内容。多页面共享接口只维护一份完整契约，注明实际提供项目、消费页面及调用差异；各页面方案保留所用接口摘要和定位链接。

接口文档按本次页面或保留消费者实际调用逐接口记录路径与方法、触发时机、身份和权限、请求字段及类型、成功响应与空值、特殊错误码、对应的用户可见提示文案与方式、必要响应消费约定、兼容说明、示例和联调验收。未确认的契约显式标待确认，不以旧接口字段或错误码自动填充。证据不足时写明待补范围，不创建空白占位页。目录与相对链接见[Markdown 交付](markdown-delivery.md)。

新接口直接写已确认的目标权限、校验、响应与预期结果，不记录 Bug 详情、编号、旧缺陷表现或修复过程；已确认修复后的契约并入正常接口定义。普通接口兼容约定仍写清，不以引用 Bug 条目替代目标契约。

### 新接口文档必须对齐落地后端（交付门禁）

逐接口按其实际提供项目分别取证和判断；一个页面调用多个后端时，鉴权、信封、错误码及定义方式不得相互套用，不为文档统一而改造项目或下游。仅写「路径前缀 + 响应信封名字」**不算**完成。生成或更新新接口文档时，核对足以证明本次约定的落地后端同端代表性实现、对应请求/响应定义、错误标识及项目规范，可复用已核验且仍适用的取证；不以固定 Controller 数量判定充分性。存在缺口或冲突时补查相关实现或规范，按下表逐项判断；任一适用门禁未通过的接口，缺少契约依据时标「待补证据」，已确认不符合适用规范时标「已知不合规、待修订」；两类均不得标为可联调契约。

| 门禁 | 通过标准 |
|---|---|
| 对照样例 | 正文写明本次采用的实现与规范依据（路由/Controller或handler、请求/响应定义、错误标识等）的路径或仓库链接、版本及所证明的约定 |
| 路径与动词 | 资源路径、HTTP 方法（GET 查询 vs POST/PUT/DELETE 写入）与落地项目同类接口一致；偏离时写依据 |
| 请求/响应定义 | 按目标项目实际约定给出拟增或复用的定义落点、名称、字段、类型及必填/可空；要求独立DTO的项目须给出类名与包路径，采用Schema、类型定义或数组校验等方式的项目须定位其实际请求校验、响应结构及序列化实现，不为门禁额外造类。上述形式均须有充分契约证据，不能把旧接口的 `data={...}`、errType 对象原样当作新契约 |
| 信封与错误码 | 成功/失败字段名与落地信封一致；未登录等通用码复用落地错误定义；仅当需前端分支且通用码不够时才拟新增业务码，并说明为何不能复用 |
| 鉴权 | 与落地项目同类入口一致的鉴权调用点（注解、中间件、JWT、员工校验等），按实际请求处理链取证，不照搬旧项目鉴权字段名 |
| 上传/附属能力 | 优先写清是否复用落地项目既有上传/配置接口；仅在无法复用时才新增接口 |
| 旧契约边界 | 明确「旧字段语义可对齐、旧字段名/错误码/信封不可直接填充」；业务文案来自已确认产品需求或旧可见原文 |

以下为项目要求独立DTO及Controller时的Java示例；其他技术栈按上表核对实际定义形式，不照搬类或包结构。

反例（不合格）：仅列出 `/api/items` 和通用响应结构，直接沿用旧接口字段，缺少目标项目同类入口和请求定义依据。

正例：引用目标项目中的同类控制器，列出已确定的请求与响应字段，定位实际使用的错误码定义。

响应消费约定限于解释接口语义所需的动作，例如未登录进入登录流程、业务拒绝时允许的后续操作，以及返回文案的展示位置。候选清理、筛选与页码切换、单条结果跳转判断、请求重试调度、过期响应处理、本地配置及请求封装参数归前端方案；接口文档引用相应方案，不展开页面实现。旧接口文档可记录旧前端实际消费行为，作为现状证据。

## 交付验收

同次迁移中若新增或修改重构后产品、新接口、测试用例或任一方案文档，交付前须完成 [四类文档集合交叉验收硬门禁](document-review.md#交付阻断四类文档集合交叉验收硬门禁) 勾选；适用的页面行为或消费者兼容摘要不得整段「见产品」而无内容。

生成、更新或正式审查文档时，按[文档审查与验收](document-review.md)核对本轮范围及交叉口径。
