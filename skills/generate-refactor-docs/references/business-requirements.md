# 重构前后产品需求文档

仅在用户要求生成、更新或正式审查重构前、重构后的独立中文产品需求文档时读取。沿主 SKILL.md 的文档口径与取证规则取得事实；目标需求依据用户指令和用户提供的需求，旧代码只提供现状证据。生成目标需求时，不用落地项目针对本次迁移已有的方案、变更规格 或迁移代码推定目标规则；若用户明确要求记录已落地实施状态，按主 SKILL.md 的已落地模式处理，并将实施状态与产品规则分开。

初稿前按[关键取证](evidence.md#初稿前关键取证)核对项目、操作、提供方及资源。

## 多页面与多端组织

迁移的端/项目范围按[主技能](../SKILL.md#选择迁移范围)选择；仅技术迁移且未请求产品交付时，不为门禁补写前后产品。实际交付或审查产品时，绿场要求仍覆盖其声明范围的全部目标规则，不能因只改一端而省略已确认的用户结果；技术方案和兼容审查则引用有效规则与决定，不要求重写整套产品。

按业务能力或流程组织重构前、后需求，各自可集中覆盖多个页面或按模块拆篇，并有统一入口；目录沿[Markdown 文档组织](markdown-delivery.md#适用范围与目录)。共同规则明确适用页面与端，差异在各适用分支写清，不按仓库结构切断业务流程，也不自行要求各端一致。

跨页面场景写清入口、交接业务信息、接收结果、返回后的状态及已确认的验证停止点；传值和恢复的技术机制归方案。拆篇后，以声明范围内的产品文档集合完成绿场检查：各篇写全自身规则，共用规则有明确主描述及定位引用，不能要求读取旧代码、接口或开发方案补齐业务答案。下文“本篇／这一篇”在拆篇时指该适用产品文档及其明确引用的同类规则。事实、目标及实现状态仍分别维护。

## 两种文档的口径

- **重构前产品需求**：描述有证据的现行产品表现，供不读旧代码的开发者理解当前业务。逐条区分“已确认应沿用”和“仅观察到、待确认”；后者可记录现状，但不得直接成为重构后需求或目标验收条件。
- **重构后产品需求**：描述把重构当作新项目时已确认的最终产品行为。正文只使用目标态，不混入旧表现或实施过程；目标行为不明确时询问用户，未得到答复前标为待确认，不自行补齐。

### 重构后产品需求交付门禁（绿场可实现）

交付前做「只读本篇 + 落地项目既有通用代码、不打开旧业务页/旧业务仓」的自检：开发者应能确定入口、各状态 UI、字段与选项、校验时机与**完整提示原文**、跳转目标地址、成功/失败结果与副作用。任一依赖「沿用旧页/旧文案/见现状或方案才能补齐」的条目视为不合格，须写入目标态原文或标为待确认。

| 门禁 | 通过标准 |
|---|---|
| 无外挂旧行为 | 正文禁止「沿用旧前端/旧文案/按原规则/同旧页」等措辞指代未写出的规则；允许在文档说明中写「不得依赖沿用旧页」类元约束 |
| 字段与选项完整 | 表单/列表的字段、必填、选项枚举、单位、空值含义写全；不能只写「著录项」 |
| 文案完整 | 按钮、旁注、校验、弹层、成功/空态等用户可见原文逐条写出 |
| 跳转可执行 | 链接文案与目标地址（含占位符含义）写明 |
| 交互时机 | 校验触发（如失焦/提交）、取消/返回、离开确认、倒计时等写明 |
| 异步表单（适用时） | 明确提交前、等待、成功与失败时的输入、提交、取消、关闭及恢复行为；允许等待中关闭时说明重开和迟到结果，无此交互记不适用；按[异步弹框约束](page-state.md#异步弹框与请求生命周期)取证与确认，不预设关闭策略 |
| 无缺陷专章 | 不写旧 Bug 编号或「修复对照表」；目标行为并入正常规则 |
| 绿场抽检 | 交付说明中声明是否做过「仅凭本篇实现」抽检；未做则标明「未做绿场独立性审查」 |
| 另议不作已确认 | 用户标「另议 / 暂不开 / 不迁移 / 待问运维」时，正文不得写成「已确认保持旧行为」或纳入必验主流程；写清当前目标态（例如页面侧不做）与待确认点 |
| 限流挂载点 | 页入口限流、业务接口限流、网关/WAF 限流分写挂载位置与用户可见结果；不可把「旧页打开时计 IP」默认写成「接口也有」或「必须等价迁移」 |
| 校验算法取证 | 格式/校验位等规则若本仓无实现，须跨相关仓或共享工具库找源码后再写入目标态；找不到才标待确认，并写已知事实与可选口径 |

用户只要求其中一种时，只产出所需文档。两份文档可以共享术语与业务事实，但各自必须能够独立说明适用用户、场景、展示、操作、判断条件、状态、业务结果与验收。

两份文档中的数值规则须能独立指导验收：

- 用业务语言写明单位、计算关系、按天折算等适用条件、计算中与展示时的精度，以及进位或舍入发生的环节。
- 写明分项与总额的关系，并给出能区分不同算法的边界示例。
- 重构前写明已核实的现行算法及其确认状态；重构后只写已确认的目标算法。旧代码能证明现状但不能证明应沿用时，标待确认；用户已明确只迁移或沿用旧逻辑时，查明本次迁移范围内的旧链路及必要交接，把已查明的用户可见结果作为重构后目标，已落地实现的不同结果另记为差异。

### 输入处理与校验的可见结果

涉及输入清理、格式转换或内容校验时，按实际字段和操作补齐下表信息，可并入现有规则、字段表或验收场景。只覆盖本页实际涉及的处理，不预设算法或另建交付物；取证方法见[输入处理与校验兼容取证](evidence.md#输入处理与校验兼容取证)。

| 覆盖项 | 必须能从产品正文确定的结果 |
|---|---|
| 操作差异 | 创建、编辑等实际入口分别如何处理同一输入；存在差异时分别写明，不合并成笼统的“文本处理” |
| 处理与校验顺序 | 哪些处理在前，校验使用原输入还是处理后的值，以及长度计数单位等判断口径；多项同时不满足时的失败优先级、能否同时提示及准确文案 |
| 保存、展示与回填 | 最终保存的文字、列表等位置显示的文字、再次编辑回填的文字；哪些转换只用于检测而不改写保存内容 |
| 区分性样例 | 选用能区分处理顺序或候选实现的输入，写明各操作的保存、显示、回填或拒绝结果；只有“兼容一致”不构成预期 |

“不支持富文本”“安全展示”描述展示要求，不能替代已确认的输入处理和保存结果。产品正文用业务语言说明可见转换与结果，函数、类、代码位置和技术映射仍放现状或方案。

分别记录规则状态：已取证且用户已确认承接的行为写入目标要求；来源冲突、行为未知或目标未决的部分列为具体待确认项；仅运行样本、部署或动态数据版本未验证的部分列为待验证。剩余验证范围不得把已查明且已确认的处理顺序、保存结果或拒绝说明一并降为未知。

## 产品与技术分离

两份产品文档的文档说明均标明现有代码所属前后端项目及可用仓库链接；用户提供旧需求文档时附其链接与版本。这些只是来源元数据，不展开代码实现。任何章节或附录都不出现旧 Bug、漏洞、修复方案或问题编号，也不出现旧代码片段、文件或类名、内部错误码、后端接口路径与字段、数据库结构。

错误与校验写触发业务条件、用户可见的**准确文案**、呈现方式（如 toast、dialog 或页面内提示）、允许的操作和结果；不能确定准确文案或呈现方式时标为待确认，不用错误码占位。页面链接的跳转目标地址属于用户可见行为，应与链接文案一起写明；尚未确认的新地址标为待确认。需要追溯时，把产品规则编号与源代码、错误码、接口字段的对应关系放在现状梳理或开发方案。

完整记录有业务意义的页面表现：不同角色与状态下谁能看到哪些区域、字段、按钮和文案，何时可操作，二次确认弹窗写什么、确认与取消分别如何处理，成功与失败后如何反馈、是否产生业务副作用。有业务意义的动态值如何显示属于产品内容：按实际字段写明适用的单位、精度、取整、时间格式与时区、状态或枚举文案、组合与脱敏规则，以及空值文案和出现条件。同一数据在不同区域的显示口径分别记录；无法从旧链路确认时标为待确认，不按字段名或接口类型推定，也不把组件样式写成产品规则。

表单写必填、格式、范围、关联校验、触发时机和逐项提示；列表写筛选、排序、默认页、页码与每页条数、条件变化时的页码处理和空结果；链接写文案与跳转目标。无需写具体颜色、尺寸等样式。

骨架图、Result、el-loading 等实现组件名和样式参数属于开发方案，除非用户明确将某种呈现作为产品要求；即使如此，也以用户可感知的场景和结果表述。无依据的文案、按钮动作、跳转、权限、金额、期限或阈值不得按习惯补写。

逐条记录有业务意义的完整用户可见文案：

- 覆盖计费说明、规则提示、按钮与链接文字、校验与失败提示、确认弹窗、成功反馈及空态文案；注明出现条件和动态数值的替换位置。
- 重构前保留已核实的现行原文，重构后使用已确认的目标原文；未确认的原文或修改不得自行改写或缩成“按原文展示”。

首次进入存在前置校验与后续必需信息串行依赖时，独立写清每阶段等待、失败、重试、跳转及正常页面出现条件；校验通过不等于页面已就绪。用户确认采用骨架图时，从校验到全部必需信息取得连续显示，任一阶段失败转失败态，重试期间回到骨架图；成功空数据与未返回、失败分别描述。接口错误说明属于动态文案时，按用户确认的服务端说明来源及中文兜底写产品规则，字段名留在开发文档。未登录沿已核实的通用登录流程；重试按失败原因决定，不按文案是否含“重试”。不要为串行流程虚构业务数据或网络请求；详细边界见 [首次初始化约束](page-state.md#首次初始化)。

按实际业务删减章节，不保留空标题。标题须标明“重构前”或“重构后”，避免两种口径混用。较长文档使用目标文档系统支持的目录；不支持时提供可跳转的章节目录。

## 推荐结构

1. **文档说明**：目标或现行能力、适用用户、场景、覆盖范围、依据和术语；标明现有前后端代码所属项目及可用仓库链接，用户提供旧需求文档时链接其版本。项目链接仅作来源元数据，不展开代码。
2. **页面与业务内容**：按区域、角色和业务状态列出字段、按钮、链接、计费说明等有业务意义的完整文案、出现条件、动态数值位置与可执行操作；不写具体样式。
3. **用户与权限**：用表格列出身份、可见内容、可执行操作和限制条件；代管、代理、未登录等只在有依据时列入。
4. **业务规则与优先级**：逐条写业务条件、判断口径、优先级、用户可见结果及后续状态。数值计算写单位、公式或等价业务关系、按天折算、计算与展示精度、进位或舍入环节、分项与总额关系及可区分算法的边界示例；时间、范围、排序、数量和空值须有明确边界。
5. **数据展示与分页**：说明展示口径、数据范围、筛选与排序、默认页、页码和每页条数、切换条件或页大小时的页码处理、总数与空值的用户可见含义。首次进入/首次查询与筛选、排序、翻页等后续请求若有不同动作，分别写触发条件和结果；后续只剩一条、空结果及请求失败也要分别判断是否跳转、保留列表或展示提示。
6. **状态与交互**：初次进入、加载、成功有数据、成功空数据、操作中、失败、重试及成功后的状态；区分初次空数据与筛选后无结果等不同场景，并写各自文案和可执行动作。
7. **用户操作流程**：按角色和场景写前置条件、操作、二次确认弹窗及确认/取消行为、反馈、结果及业务副作用；链接或按钮跳转写准确文案和目标地址，不把不同分支藏在“按原规则”中。
8. **表单与异常提示**：逐字段写必填、格式、范围、关联校验、校验触发时机、准确提示文案；接口失败按业务条件写用户可见文案、toast/dialog/页面内等呈现方式、可执行动作和结果。文案或方式不明确时列待确认，不出现内部错误码。
9. **验收场景**：按“用户/前置条件 → 操作或触发 → 预期展示与文案 → 业务结果/副作用”列出可执行场景。
10. **待确认事项**：写已确认事实、问题及不同答案对目标行为和验收的影响；没有时写“无”。

可按业务需要增加目录、术语表、支付或状态转换等专章；各篇口径及技术内容边界按前文执行。

## 共同交付检查

| 检查项 | 通过标准 |
|---|---|
| 来源与口径 | 重构前、后文档各有明确依据；观察到的现状不冒充目标规则 |
| 用户与场景 | 角色、入口、业务目的和范围明确 |
| 判断与边界 | 每项规则有条件、优先级、边界和结果 |
| 数值计算 | 金额、天数和档位的单位、计算关系、精度、进位/舍入位置、分项与总额可按边界示例验收；未确认处不自行补齐 |
| 展示与操作 | 各状态的内容、准确文案，以及动态值在各展示位置的适用口径和空值文案、按钮与去向可独立实现 |
| 业务文案 | 计费说明、规则提示、操作文案、弹窗和反馈均有完整原文、出现条件及动态数值位置 |
| 交互与跳转 | 二次确认的确认/取消行为、链接文案与目标地址明确 |
| 表单与分页 | 校验条件和时机、逐项文案、筛选排序及分页状态转换明确 |
| 提示方式 | 各类错误的用户可见文案及 toast、dialog 或页面内呈现方式明确 |
| 副作用 | 何时产生记录、支付、通知或其他业务变化明确；不应发生时也明确 |
| 异常与空态 | 初始化失败、交互失败、初次空数据与筛选空数据等适用场景区分清楚 |
| 验收 | 只阅读这一篇产品需求，也能按用户、条件、动作、展示和结果逐项实现并验收关键行为；遇到“按旧规则/沿用旧文案”等外部依赖时必须补齐目标态规则或标出阻塞范围。重构后文档另须满足 business-requirements.md 中的「绿场可实现」门禁 |
| 产品边界 | 符合[产品与技术分离](#产品与技术分离)，不混入问题与实现信息 |
| 来源信息 | 现有代码所属项目、可用仓库链接及用户提供的旧需求文档链接齐全 |
| 待确认 | 影响业务结果的歧义显式列出；重大未决规则不标为可完整验收 |

对每条规则检查：谁在什么条件下触发、使用哪些业务信息判断、条件冲突时何者优先、成立与不成立分别展示什么、允许做什么、完成后进入什么状态、临界时间和特殊身份如何处理。无法确定且会改变业务结果时列为待确认，不自行推断。

## 生成、审查与交付

生成或更新前按本篇的[推荐结构](#推荐结构)与[共同交付检查](#共同交付检查)删减章节。完成指定页面与直连接口的一轮取证后、撰写文档前，汇总仍影响业务规则或用户可见内容的问题，附已知事实、可选口径及其影响，一次向用户集中确认；不要逐项打断，也不要等成稿后才提问。已有明确答复的不重复问；未获答复时在文档中标为待确认，继续完成可确定部分。撰写中发现新的关键歧义时及时补问。用户要求「不参考已有迁移文档、重新生成」时，仍须遵守本会话已确认的目标决策与另议口径，不得因重写而把另议项改回「保持旧行为」。

审查时对照用户指令、用户提供的需求、现状证据和目标决策，指出遗漏、矛盾、技术泄漏与待确认项；产品文档本身不展示旧问题及修复过程。

再仅凭重构后产品需求逐条重建入口、首次查询、后续筛选/排序/翻页、空态、失败与跳转后的业务结果：缺少判断条件或需翻阅旧代码、开发方案才能确定的用户行为，补入产品规则或明确标为待决策。失败、重试、未就绪等态须写出准确提示原文与按钮文案，不得以「可重试」「通用错误」代替。未经要求不改文档或代码。更新已有 Markdown 文档时，按[Markdown 交付](markdown-delivery.md)保留用户最新修改并核对正文；同次交付新增或修改四类中任一文档时，必须完成[四类文档集合交叉验收](document-review.md#交付阻断四类文档集合交叉验收硬门禁)勾选后再声称合格。

按角色、前置条件、用户动作、展示/准确文案及提示方式、业务结果写验收场景。覆盖主流程、权限差异、不同状态 UI、确认弹窗、表单校验、筛选分页、链接跳转、关键边界、空数据、异常与副作用；不以“功能正常”“按原规则”替代可执行条件。重大目标规则尚未决策时，明确标注未定范围，不声称整份目标需求已经可以独立验收或开发。

新建或重大改版、且文档需独立指导开发时，若任务规模和可用条件支持，委派未参与撰写的 Agent 从开发者视角反向审查：能否仅凭文档确定展示、操作、条件优先级、角色差异、边界状态和业务结果。是否创建新会话由用户明确决定，不作为默认审查步骤。无法安排独立审查时如实标记，不声称已通过；普通修订针对改动条目及其关联规则核对即可。交付时说明覆盖范围、依据、待确认项和实际完成的审查。文档工作不授权修改代码或发布。
