# Bug 汇总与修复方案

生成、更新或审查迁移范围内的 Bug 记录、原位标记或修复引用时读取。此文档独立于现状梳理和迁移方案，集中维护 Bug 详情与修复设计；只处理用户要求的交付物和已授权范围。只审查时报告缺口，不自动建文档或发布；无问题时不创建空白占位文档，需要的汇总文档未获授权时列为待补。

同一问题跨页面、端或项目时沿用同一稳定编号，在一个条目中记录多个来源、实际修复对象和各对象实施/验证状态；相似现象尚不能证明同一原因时不强行合并。各页面现状与旧接口按实际发生位置引用，关闭结论明确覆盖对象，不能由一个项目通过推定全部完成。目录与其他内容归属沿[归属规则](document-review.md#文档归属与同步)。

## 登记与确认

- 标明页面、调查范围、来源版本及相关文档。区分已观察事实、已确认 Bug 与待核实问题；只有可定位证据和明确判定依据才能标为已确认 Bug，不能因“不合理”或身份、权限不明的成功请求就认定越权。
- Bug 是否成立、修复对象及范围分别记录。只有修复已获确认且目标口径与兼容影响明确时才安排实施；已有待核实、范围外或暂不修复条目保留其依据与决定，不自行升级为任务，也不把“不阻断本次”写成已修复或已接受全部影响。
- 新链路承接旧缺陷且旧实现未改时，按已确认的新页面与新接口确定修复对象；旧入口作为缺陷来源或调用关系记录，其保留本身不增加风险登记、后续任务或关闭条件。实际改动共享实现或契约时，按真实影响检查保留调用方；用户明确要求同步修复的旧入口也纳入目标及验收。调用方记录位置见[旧接口文档](business-analysis.md#旧接口文档与发布)。
- 按需用简短索引表列编号、主题、确认状态、修复范围和实施/验证状态，详情写在每个编号的独立条目中。索引按实际范围区分本次修复、后续评估、已接受限制等安排；这些范围状态不等于修复完成。编号沿用既有唯一 ID；新编号可由业务域、类型与稳定序号组成，不因排序、关闭或增删而重排。通用状态和关闭要求可集中一次，各条保留专属证据、兼容范围及关闭条件。

## 每项内容

| 内容 | 记录要求 |
|---|---|
| 触发与现象 | 入口、角色/权限、输入、步骤、实际结果及影响；链接现状梳理、旧接口的实际发生位置，区分缺陷现象和正常分支。 |
| 判定与诊断 | 与哪项已确认规则或权限边界冲突、原因及可定位证据；标明项目、版本/环境和未核实部分，不把猜测写成结论。 |
| 目标与范围 | 分开写旧缺陷来源与本次修复对象、正确目标及决定依据；已有范围状态沿用其真实含义，业务口径未定时明确受阻分支。 |
| 修复方案 | 本次修复对象在前端、后端、联调的实际落点、职责、处理顺序与依赖；涉及共享改动或已确认同步修复时，写清相应调用方的兼容影响，不由调用关系扩展任务。 |
| 验收与追溯 | 链接已存在的目标需求、接口、迁移任务和用例；能制造原触发条件并按修复后的正确结果判断，覆盖本次修复对象及实际共享影响的必要副作用与旧入口。缺少的规则、用例或条件明确待补。 |
| 关闭条件与证据 | 对本次已确认修复对象列出实施与验证条件，分别记录未实施、已实施未验证及验证结果；完成或关闭状态注明对象及实现、执行证据。方案定稿、用例已设计不等于完成；新入口通过不能代替已纳入的旧入口或实际共享影响验证。范围外仍存在的旧缺陷不标为已消除，也不成为本次修复任务的关闭条件。 |

## 编号与文档引用

为每项编号设置唯一、稳定且可直接定位的条目锚点；不支持表格行锚点时使用编号小标题。关闭后保留条目与锚点，更新状态和证据，不删除历史旧行为来源。

- 现状梳理、旧接口：在原描述位置标记“此处存在 Bug：编号”，编号链接此文档具体条目；实际旧行为仍完整保留，不另设汇总或复制诊断、修复方案。
- 迁移方案：在涉及修复的任务旁注明“修复 Bug：编号”并链接本条目，Bug 详情与修复设计不在方案重复维护；常规迁移实施安排仍归迁移方案。
- 两份产品需求、新接口和用例：不记录 Bug 内容或编号。重构前产品描述实际业务表现，重构后产品与新接口写完整目标规则；用例采用修复后的目标预期，不把旧缺陷结果当兼容要求，不要求另立修复用例章节。追溯由本条目指向目标规则、接口和用例，不要求它们反向标记 Bug。

交付前核对所有原位/任务编号与条目一致、条目能回到对应来源，已纳入修复的条目具备目标及用例覆盖；不为追溯强行补建未授权文档。文档条目定位按[Markdown 交付](markdown-delivery.md)验收，设计归属与覆盖按[文档审查](document-review.md)检查。
