# 页面状态与交互

编写迁移方案、审查落地结果或设计迁移结果测试时读取；产品交付涉及首次初始化时，只需读取对应章节并提取用户可见行为。产品需求文档只保留用户可感知的业务表现和已确认文案，不照搬组件配置或接口字段；加载与空态若属于已确认产品要求，用用户场景和结果表述。

## 首次初始化

涉及首次初始化时，核对旧服务端前置校验在独立前端中的承接能力，以及“校验通过”与“全部必需信息就绪”的区别；串行依赖的骨架图、失败和重试规则见 [首次初始化约束](page-state.md#首次初始化)。产品交付只读取其中与用户可见状态相关的规则，目标呈现以用户确认和目标项目约定为准。

列出实际发起的请求、依赖顺序、并发结束条件和负责的页面区域。分别确定未返回、成功有数据、成功无数据、业务失败、请求失败、登录跳转时的状态；未返回不等同于空数据。多区域页面明确局部失败是否影响其他区域、标题和导航何时结束占位，以及重试范围、防重复触发和再次失败后的状态。

### 前置校验与必需数据串行依赖

旧服务端校验登录、员工身份或店铺后才返回页面，迁入独立前端时核对是否已有可供前端调用的等价校验能力。缺少时，若补齐能力属于已授权的迁移规划范围，在方案中规划等价只读能力；若超出范围，只记录依赖缺口、范围冲突及受阻分支，不自动新增接口、后端开发或部署任务。规划不授权自行实施接口。公共头部完成请求、成功信封或缺少店铺字段，不能代替完整校验；须能区分确认无店铺、明确无权限、依赖服务暂时故障。入口权限与具体业务操作权限分别取证，前端门禁不代替业务接口自身鉴权。

按实际依赖分清前置校验、必需业务初始化、可独立加载的局部信息及本地配置；只在前置成功后发起依赖它的请求。列明使正常页面就绪的必需项；本地配置无需增加网络请求，用户主动查询不自动成为初始化请求，也不为凑串行链虚构业务数据。没有后续必需远程数据时，校验及必需本地信息就绪即可显示正常页面。

用户确认或目标项目约定采用骨架图的串行初始化按下列状态核对；已有明确不同呈现要求时依其执行，不将本规则反写成旧页面现状：

| 阶段或结果 | 页面与后续动作 |
| --- | --- |
| 前置校验等待中 | 显示骨架图，业务操作不可用，不发依赖请求。 |
| 校验成功、必需业务数据未就绪 | 连续显示骨架图，不提前显示正常 UI，也不短暂显示空态。 |
| 全部必需项成功 | 显示正常内容；合法空数据进入该业务已定义的空态。结构缺失或失败不能当作空数据。 |
| 任一必需阶段失败 | 转页面失败态，停止后续依赖，业务操作继续阻断；可恢复故障有重试，明确无权限等不可恢复故障无重试。 |
| 未登录或需业务跳转 | 沿已核实的公共登录拦截或业务跳转；跳转期间不闪现页面失败态，不提供无效重试。 |
| 重试中、再次失败 | 重试期间回到骨架图并保留失败上下文；全部必需项就绪才显示内容，再次失败回失败态。 |

错误说明先核对目标项目真实响应字段和请求封装；用户指定展示接口文案时，使用契约允许展示的说明字段，写清字段缺失和无业务响应时的中文兜底，避免公共提示与页面重复。保留错误分类以决定阻断、跳转和重试，不能从文案是否含“重试”推断可恢复性，也不能把服务超时当作明确无权限或无店铺；不自行替换已确认的服务端说明。

写明重试起点：前置失败重新校验；后续必需数据失败时，只有仍有效的身份/店铺上下文及已成功数据才可复用，重取失败阶段及后续依赖。登录/店铺上下文失效、账号或店铺切换、整页重入时重新走前置流程；重试防重复触发，失效批次响应不能放行页面。初始化成功后的搜索、筛选或翻页按下一节处理，不退回首次初始化整页态。测试按实际阶段覆盖校验成功但数据仍等待、合法空数据、各阶段失败与重试、跳转及失效响应；不存在的阶段标明不适用，不虚构接口或交互。

加载、失败和空数据呈现先核对目标项目的现有组件与已确认设计，再确定占位、错误态和重试交互。若采用骨架图，形状应贴近实际内容并检查组件默认样式与页面样式的冲突；若采用 Result，按该项目能力确定类型、尺寸、主题、描述和按钮状态。业务失败优先使用已确认的用户可见文案；仅在接口契约明确允许、内容安全且不与产品需求冲突时展示服务端文案，并提供兜底。请求失败使用项目的通用错误呈现；登录跳转期间不短暂展示错误态。重试期间保留错误上下文，成功后再显示内容；项目已有明确重试约定时依其执行。

## 初始化后的请求与操作

首次初始化成功后的查询或操作不重置为首次加载态。搜索、翻页、筛选和刷新需明确旧内容、条件、页码的保留或更新、空结果、失败提示、并发取舍与取消行为；失败不得无依据地重置整页。若目标新增统一提示或显式重试，先确认它与旧页的可见行为差异；写明准确文案、重试使用的请求条件快照，以及新旧请求交错时哪些结果可以更新页面。局部加载方式按目标平台和项目习惯确定，不将 PC 做法直接套用于移动端。

有表格时区分初始查询为空、筛选后为空和请求失败：各自确定说明文案、可执行操作和呈现组件，使用目标项目已有空态方案或已确认的等价设计，不预设 Result。

保存、删除、隐藏、结束、试算和支付等操作需明确提交期间的禁用范围、重复触发、副作用顺序、字段错误与一般错误展示、失败恢复，以及成功后回填或重新查询。身份或前置校验失败时，核对不应发生的下游调用和写入。

存在页面离开与重入时，区分请求批次、编辑会话及页面实例；核实路由卸载、复用/缓存与整文档导航的实际生命周期。旧实例不得操作重入后的新实例，这是实现归属约束；跨页是否继续反馈按已确认目标处理，只有真实目标歧义才列决策，不重问已确认的退出策略。未规定的分支只影响相应门禁，不默认取消所有请求，也不新增软账号切换、轮询或取消能力。

目标要求离开后停止原页提示、刷新或跳转时，检查每个副作用的实际触发位置，包括先于页面回调执行的公共拦截器；只在页面then/catch判断失效不能阻止此前已发生的提示或登录跳转。按请求来源与页面实例安排必要的局部承接，不把原页策略推广到已确认继续的后台任务或其他页面。

### 异步弹框与请求生命周期

仅在页面存在弹框内异步写操作时核对本节；同步本地操作或不存在的退出方式记为不适用，不为凑场景新增请求、控件或状态。关闭策略依据用户确认或已授权的兼容基线，可以允许也可以禁止；某页“保存期间禁止关闭”的决定不能成为其他页面的默认规则。

取证时把打开、输入与校验、发起请求、等待中再次操作或关闭、成功或失败、可能的重开与迟到响应串成一条流程；分别查明关闭处理是否中止客户端请求，以及回调读取原请求快照还是可变的当前弹框。关闭弹框或中止客户端请求均不能证明服务端未写入或已回滚。旧代码只证明现状；影响目标结果的缺失或冲突先列具体待确认项，不把旧异常直接写成目标。

同页关窗后的反馈规则与页面离开分别判断，不能互相套用；页面实例的失效与副作用承接按上一节核对。组件卸载本身不证明Promise回调已取消或服务端写入已结束。

| 实际存在的阶段 | 需求与方案必须确定的内容 |
|---|---|
| 未提交或前端校验未通过 | 输入、提交、取消及各关闭入口是否可用；关闭后草稿如何处理 |
| 请求等待 | 输入能否修改，重复提交如何处理，取消及关闭按钮、遮罩、Esc等实际入口是否可用；不能只写“保存按钮禁用” |
| 成功与各类失败 | 提示、输入保留、哪些操作何时恢复，以及关闭、跳转或刷新顺序；字段、一般业务和网络/超时按已确认语义分别说明 |
| 允许等待中关闭并重开 | 原请求的反馈和列表刷新是否仍发生，旧结果能影响哪个编辑会话；分别核对重开同一记录和另一记录，不让原请求误改新框的输入、错误或可操作状态 |

产品文档只写用户可见结果，参数快照、响应归属及失效处理放开发方案。规则未确认时标明受阻分支，继续完成可确定部分；不默认增加服务端取消、幂等或轮询能力。

“失败恢复原输入”等表述须明确指提交时值还是等待期间最后编辑值。输入可编辑时，用“提交甲、等待改乙、分别成功/失败”的一组操作区分请求值、保留值和关闭后的未提交内容，不以快速失败样例代替等待阶段。

### 前端修改排序

**前端修改排序**：涉及单个列表项的位置调整时，读取[前端修改排序指导](page-state.md#前端修改排序)。先核实旧逻辑，不存在已识别的排序一致性问题时允许沿用；拖拽与箭头方案可向用户提出建议，确认后采用，不强制替换旧逻辑；不适用于整个列表的正序、倒序排列。

本节适用于单个列表项修改排序位置，不适用于按字段正序、倒序等整个列表重排的交互。先核实旧代码的 UI 更新时机、接口成功/失败语义及失败处理；旧逻辑不会产生已识别的排序一致性问题时，允许按已确认的迁移范围沿用，不因其不同于下表就认定缺陷、强制改造或阻断交付。

按用户实际交互判断适用范围；单项换位即使请求携带全量 ID，也不因此成为整个列表重排。用户已明确接受失败后的前后端差异时，不以消除该差异为由新增恢复查询、完成判定或下游改造要求。

下表是可向用户提出的建议方案，不是默认硬性要求。交互方式、UI 更新时机及失败处理分别依据已确认目标或已授权的兼容基线；仅选择拖拽交互不代表确认其余列。尚未明确的部分列具体待确认项，不能自行采用表中策略；已有明确决定的按已确认目标执行，不用建议自行替换。

| 建议交互方案 | 序号变化范围 | UI 更新时机 | 请求失败处理 |
|---|---|---|---|
| 拖拽排序 | 被移动项及其相邻一批列表项，邻项至少1条 | 允许更新 UI 的同时发起排序请求 | 仅按具体业务的默认失败规则处理，如 toast 或业务特殊要求；不恢复之前的排序，不要求重新查询以消除前后端排序差异 |
| 上下箭头等相邻换位 | 被移动项与相邻一项 | 先发起请求，按请求结果渲染；只有接口确认数据处理成功后才更新 UI | 等待中或处理失败时保持原顺序，失败提示按具体业务规则处理；不能仅凭 HTTP 成功认定数据处理成功 |

采用上述建议时，按交互分别判断，不用通用“失败恢复”要求覆盖已确认方案。只有已向用户说明并获明确接受“不恢复旧顺序、不重查，失败后显示可能与实际保存顺序不同”，或已有有效决定明确接受该影响时，才将该差异记为已接受限制，不列为必须修复的缺陷或交付门槛。已有接受决定不重复询问；仅选择拖拽不覆盖原有的失败恢复决定。
