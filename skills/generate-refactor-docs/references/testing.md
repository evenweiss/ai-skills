# 迁移结果测试

设计 Markdown 用例或对照历史用例时读取。审查报告中记录测试缺口。涉及页面交互时再读取[页面状态与交互](page-state.md)中的相关小节。

## 多页面与多项目覆盖

按[迁移范围](../SKILL.md#选择迁移范围)选择测试层级：仅前端验证真实交互、请求与响应消费，不把页面 Mock 当作后端处理证据；页面相关的仅后端验证入口、鉴权、处理、副作用、实际旧消费契约及受影响结果，不强制补整页 UI 用例。指定项目核对其入站/出站边界与真实共享影响；全栈再贯穿范围内两端。未修改项目不自动成为开发任务，但关键兼容不能因单端范围而跳过。没有独立需求/新接口篇时，可用已确认规则、既有契约和有效决定作为预期来源，缺少决定或证据则保留受阻分支，不从实现补答案。

用例可按业务场景、模块或测试层级组织，拆篇后保留统一覆盖与执行入口。复用来源映射串联业务场景、页面与端、接口提供项目、实施落点及用例，不为映射另建文档。跨页面交接、返回恢复和已确认端差异须有贯穿预期，不能由各页单独成功推定整条链路通过；已确认仅核对发出跳转时保持该停止点。

共享接口变化按实际消费差异检查受影响页面，多后端链路分别明确可控制依赖和观察位置；页面 Mock 不证明后端内部调用或跨项目副作用。仅依赖项目不自动成为改造或全面回归对象。测试用例写条件、步骤和预期，执行记录写版本、环境、结果及证据，可同篇或拆篇；两类状态不得混同。

## 迁移结果测试用例

生成或补齐迁移验收用例时，无论迁移是否已实施，均站在测试人员角度，依据已确认的迁移需求文档、迁移方案、新接口文档及用户后续明确确认的目标决定设计用例；记录后续决定的来源和与既有文档的差异，不因测试任务自动改写文档。先核对文档版本，再按用户角色和业务状态写清前置条件、测试数据、进入页面的方式、操作步骤，以及每一步可观察的页面、跳转、请求和业务结果；建立“来源条目 → 用例 → 预期结果”的对应关系。产品行为以已确认的迁移需求及后续明确确认的目标决定为准；迁移方案与新接口文档提供技术契约和联调口径。

维护已有用例时，保留稳定编号与锚点，用完整目录覆盖所有当前用例；按业务或测试层级分组即可，不因重排而重编号。新增和专项用例进入同一目录，详细步骤、分层控制及夹具归到对应编号；共享矩阵有明确适用编号和定位引用。既有条目已能覆盖补证时直接补齐，目录、正文、来源及数量/执行状态一起核对，不另追加一份日期用例表。来源须与实际操作和预期相符；范围变化按[文档交叉核对](document-review.md#文档更新与交叉核对)检查各列，不只修改摘要或确认编号存在。

涉及已确认 Bug 修复时，用例按**修复后的目标逻辑**设计，范围依[Bug 修复对象与共享影响](bug-register.md#登记与确认)确定：原触发条件可作为测试输入，预期必须是已确认的正确结果，不能把旧 Bug 表现当作兼容预期。执行中仍出现旧表现应记失败，不能改预期使其通过。相关场景可并入权限、边界、异常或兼容用例，已有用例足以区分正确结果与旧表现时不重复新增，也不要求另设“Bug 修复用例”章节。测试文档不记录 Bug 内容或编号；覆盖关系由独立 Bug 文档链接到目标规则、接口和用例维护。

通常不为设计用例全面重取旧项目代码或目标项目的通用架构；当历史 QA 用例与“沿用旧逻辑”的目标或现状证据冲突，或用户专门要求核实旧行为时，只针对争议分支核对旧实现或可靠实测。历史用例本身不证明现行行为；若“沿用旧逻辑”的决定明确覆盖该分支，且旧实现或可靠实测足以确定行为，就以核实的旧行为作为兼容基线并记录与历史用例的差异。只有证据互相冲突、决定范围不明或确需改变行为时才列待确认，不凭旧用例或代码自行创造目标规则；文档与后续明确确认的目标决定冲突时，以该决定设计受影响的预期并标记文档待更新；其他文档缺失、版本冲突或缺少决定时，先列出可确定的用例与受阻场景，说明所需文档或决策；不用落地代码、现有测试或相似页面填补预期。

设计涉及跨层调用或分阶段等待的用例时，写明测试层级、可控制的请求或依赖，以及可观察结果。页面只调用聚合接口时，页面用例控制聚合请求的等待与返回；内部依赖的顺序、等待、调用次数和副作用由后端用例验证。前端实际发起多个独立请求时，才按各请求边界控制。跨层联调用例须说明依赖控制与观察手段；条件缺失时标受阻，不把内部处理阶段写成页面可直接操作的阶段。上述边界在用例设计时确定，不要求提前读取测试框架或编写自动化代码。

在现有用例列中指出“控制哪一层的什么输入/依赖、观察什么结果”。页面Mock证明请求和呈现，适配桩证明转换，实际查询构造证明谓词；真实数据命中仍需对应环境验证。相互一致的Mock响应或自写匹配器不能替代提供方结果证据。

涉及[依赖失败与安全展示](evidence.md#动态展示值)时，后端控制真实依赖的零值/空结果、失败与异常，观察信封及后续调用；页面在实际请求边界控制成功/失败，核对准确呈现。按发现的分支选能区分错误实现的组合，例如合法零值下的文本展示与回填，不能用单个普通成功样例证明失败语义或安全保护完整。

用例设计、测试执行和迁移实施分别记录状态。未实施的页面可以先设计用例；待执行用例不能记为通过，也不能据此宣称迁移已实施或验证完成。

用户要求比对既有用例时，差异表分别记录历史用例要求、已核实的旧行为、已确认目标及决定依据，并关联受影响的新用例；未核实的旧行为标为待核实。已确认规则须落入用例正文和可观察预期，不能只写在差异表中；已有差异汇总章节时同步核对。配套需求或方案正文缺少该规则时，按主技能的文档归属和授权范围更新，未授权则列为待同步。涉及 Bug 的旧表现、诊断和修复对照归独立 Bug 文档；用例文档只保留目标规则、操作、预期、正常来源及待同步项，不附 Bug 详情或编号。没有比较任务或既有差异章节时，不为此强行新增章节。

多条用例或新旧差异对照宜用表格呈现，使用业务人员能读懂的场景、操作与可观察结果，不以接口码或函数名代替预期。

前端用例须验证真实交互，不以组件方法或接口函数的单元测试替代页面验收：覆盖可见与禁用条件、点击和二次确认、输入校验、筛选分页、链接与支付跳转，以及初始化、加载、成功空态、业务/网络失败、重试和失败恢复等实际适用的状态。逐步核对文案、提示方式、操作是否可继续、页面数据是否保留或更新，并检查前后端请求及副作用符合文档。页面没有的交互不虚构。根据风险和环境选择浏览器端交互测试、组件测试、接口测试或可执行的人工用例；能自动化的关键用户路径优先在页面层验证，仅靠代码断言不能声称交互已通过。

涉及[异步弹框](page-state.md#异步弹框与请求生命周期)时，用受控Promise、下游桩或明确的人工等待步骤保持请求未完成，再实际尝试修改、重复提交、取消及各关闭入口；分别验证成功、失败后的输入和可操作状态。按已确认策略验证关闭被阻止，或关闭后重开同一/另一记录并放行原请求的成功与失败；不只测试提交前取消、普通成功和快速双击。重大交互规则仍未确定时列出受阻场景，不从旧实现补写目标预期。

页面离开/重入与同页关窗分别制造；有相关目标时，在原实例失效、重入后放行迟到成功、失败及登录类响应，核对原页副作用和新实例状态。验证保留决定结果的公共请求处理顺序；把公共拦截器替换为空函数或只测页面回调，不能证明提前触发的提示/跳转已被隔离。缓存页面及已确认继续的后台任务按各自目标，不机械套用卸载策略。

后端与接口用例覆盖实际适用的身份权限、成功、空数据、失败、错误码及类型、金额与时间边界、副作用及旧调用方兼容。记录建议的验证层级和执行前置条件。已有执行结果只有在具备对应版本、环境和证据时才能引用。

生成、更新或正式审查文档时，按[文档审查与验收](document-review.md)核对本轮范围及交叉口径。
